Two pipelines, one door

A BJJ video and a user's voice note never meet. They are processed by two completely separate pipelines that touch at exactly one place — and that place is a single string substitution.

The idea worth keeping

Almost everyone who reads this codebase tries to hold it as one long chain: video goes in, cue comes out. That model makes the whole thing untraceable, because the two ends are separated by weeks, by different languages, by different machines, and by a deliberate legal boundary.

Hold it as two pipelines and one door instead:

Build time — offline, once per instructional, on your Mac
1. Video~/Documents/BJJ Instructionals
2. Transcriptscripts/transcribe.py
3. Recordsscripts/mining/mine.ts
4. Repairrecords.ts:309
5. Enrichmining/enrich.ts

7. Publishmining/publish.ts
▼   THE DOOR   ·   public.coaching_records   ·   ▼
Run time — per user session, ~10 seconds, in a Deno edge function

2. TranscriptWhisper + vocabulary

Nothing crosses that door except distilled mechanics. Not the video, not the transcript, not the quote, not the instructor's name, not a timestamp. That is not tidiness — it is the reason the project is legally safe to run, and publish.ts physically refuses to run when something tries to sneak through.

The boundary, in three lines of code

DROPPED_FIELDS = ['quote', 'source', 'chapter'] (publish.ts:20) — deleted.
scrubNames() (:116) — partner names and "this video" neutralised.
findLeaks() (:176) — scans the output and aborts the publish if any marker survived. It runs on what is about to ship, not on what you meant to ship, which is why it catches leaks nobody anticipated.

What a "record" actually is

The unit that crosses the door is roughly 60 words distilled from 90 seconds of speech. On the build-time side it carries its evidence; on the serving side it has been stripped of it.

Notice the id row. A serving id derived from the review id would itself be a citation, so publish maps between them through id-mapping.json — and that mapping is also what keeps a human's certification alive when a volume is re-mined. There is deliberately no mistake field. Instructors state mistakes as prohibitions ("never bridge straight up"), so the mistake is already the negative half of the prescription. A separate field would be the model restating itself with no quote able to back it — see records.ts:33.

The door has a lock: three gates

Having records for a position is not enough to use them. Between the table and the prompt sit three filters, each added because the obvious behaviour was measured and found to be worse.

GateWhereWhy it exists
gi context process-session/index.ts:488 Applied before ranking, so a record that cannot apply never occupies one of the 20 slots. What the recording says beats a stale UI toggle.
relevance ≥ 2 grounding.ts:31 The one to remember. Injecting the top 20 records for a position made cues worse — a blind trial preferred the ungrounded cue two-to-one. Right position, wrong problem. The model built a confident, specific cue around a mechanic answering a different question.
review state grounding.ts:213 rejected and contested records are excluded outright; certified is only a tiebreak. With 0 of 1,322 records certified, making it a gate would have grounded nothing at all.

The sentence to take away

Specificity is worthless if it is aimed elsewhere. That is the whole justification for the relevance gate, and it is the failure mode you will look for first when a grounded cue is bad.

And then: the door itself

All of that selection produces a list of records. One function turns that list into prompt text — groundingSection(), at src/sports/grounding.ts:276. It returns a block of guidance plus the mechanics, and it returns the empty string when there is nothing to inject, so an ungrounded cue is byte-identical to a cue from before grounding existed.

That block reaches the model through exactly one substitution. In src/sports/bjj/bjjPrompts.ts:150, the coaching prompt ends:

- Dominant weakness so far: {{DOMINANT_WEAKNESS}}{{GROUNDING}}

That placeholder is the door. Everything upstream — 88 volumes, 40 hours of GPU transcription, 5,000 mined records, the splice repair, the enrichment pass, the leak guard, the certification votes — exists to put text into {{GROUNDING}}. If that one substitution does not happen, the entire build-time pipeline has no effect on any user, and nothing else in the system will tell you.

Finding — verify this yourself, it takes 30 seconds

The client reference implementation fills it (src/providers/ai/ClaudeProvider.ts:89). The server — the one that actually serves users, per docs/PIPELINE.md — does not.

In supabase/functions/_shared/ai.ts, generateCoaching (line 260) takes a groundingRecords parameter at line 268, imports groundingSection at line 10 — and its fillTemplate call at line 270 has no GROUNDING key. The parameter is never read.

Run this:

grep -n "groundingRecords" supabase/functions/_shared/ai.ts

One line comes back: the parameter declaration. A value that is passed and never read.

Work out the consequences before reading on — this is the exercise, and it is the exact reasoning the mission asks for. Then check yourself below.

If {{GROUNDING}} is never substituted server-side, what does the live model receive?

The literal text. fillTemplate only replaces keys it is given, so the seven characters of the placeholder are sent to Claude verbatim as part of the prompt, and no mechanics follow them. The call succeeds. The cue comes back. Nothing errors.

What does the sessions row then record for that cue?

It says grounded, and it is wrong. Selection, arm assignment and logging all happen in index.ts:486–504 and all succeed. The write at line 548 records the arm, the count, and — since migration 018 — the exact grounding_record_ids. Every one of those columns describes a treatment that was never applied.

What does that do to the grounded-vs-withheld A/B experiment?

Both arms are the same arm. The withheld arm passes an empty array; the grounded arm passes a full one — and both are discarded at the same line. Any difference measured between them is noise. The experiment cannot be salvaged retrospectively, only re-run.

Which existing test suite would have caught this?

None of them. tests/unit/grounding.test.ts tests groundingSection in isolation and it works. tests/integration/FlowlogPipeline.test.ts tests the reference implementation, which fills the placeholder correctly. There is no Deno test anywhere under supabase/functions/. The bug lives precisely in the gap between "mirrored by hand" and "verified".

What is the general lesson this repo keeps re-learning?

Silent no-ops. This is the third instance on record. Issue #75: transcripts without timestamps were skipped by the miner and the series "mined successfully" while producing nothing — 415k words. The volume numbering collision: 13 transcripts were invisible to every mining run, for as long as the corpus existed. And now this. In all three, every step reported success. Whenever you add a stage here, ask what its output looks like when it does nothing — and make that look different from working.

What you can now do

You can trace a cue in both directions. Forwards: a video becomes a transcript, becomes records with quotes, gets repaired and enriched, gets stripped and published as opaque rows. Backwards: a session row names its grounding_record_ids, those point at serving records, and id-mapping.json on your Mac maps them back to review records that carry a quote and an H:MM:SS into a specific volume.

And you can name the one join between the halves — {{GROUNDING}} — which is where the next several lessons will live.
